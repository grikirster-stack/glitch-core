# ADR-002. Сетевая игра по локальной сети: хост и подключение, вид и ник игрока, баланс кооператива

| Поле | Значение |
|---|---|
| Статус | **Предложен** (реализуется по волнам § 5.2, не больше двух PR в волне) |
| Дата | 2026-11-02 |
| Снимок кода | `main` @ `f47087d` (после PR #76 «Сохранение») |
| Продолжает | ADR-001 (`docs/adr/0001-core-loop.md`), § 5.4 «мультиплеер — не в этой версии» |
| Авторы | координатор + Claude |
| Обсуждение | PR #PR_ADR (issue #82); issues #MPA–#MPL — по одному на PR плана (таблица в § 5.3) |

> Запрос владельца: «игра по сети, для начала по локальной сети. Игрок выбирает себе вид и ник;
> кто-то создаёт игру, кто-то подключается». Интернет-игра (NAT, ретрансляторы) за рамками
> этого ADR: подключение по IP с пробросом порта работает «бесплатно», но не проектируется.

## 1. Контекст

### 1.1. Что уже есть и что пригодится сети

| Что | Состояние на `f47087d` | Чем полезно сети |
|---|---|---|
| Автозагрузки | `DB`, `World`, `Game`, `Sfx`, `UI`, `Tech`, `Lore`, `Threat` — глобальные синглтоны процесса | одно место для «режима сети»; но две копии игры в одном процессе невозможны (§ 4.10) |
| Генерация мира | детерминирована сидом: тайлы, руины, терминалы, лор, тайники | клиент строит тот же мир сам по сиду (замер: 0.96 с), по сети идут только отличия |
| Сохранение (#37) | `Save.gather()` — словарь простых типов, у каждой системы свой `save_state/load_state`, у каждой машины — через `super` | готовый **снимок для входа в игру**: 22.9 КБ свежий мир, 23.8 КБ база из 130 машин (замер § 9.1) |
| Загрузка | `Save.apply()` поверх мира того же сида правит только отличающиеся клетки: 9–35 мс | клиент применяет снимок за десятки миллисекунд |
| Шов ввода | `Player.test_input` (`keys`, `mouse`, `mouse_buttons`) — им управляют все 48 сценариев | **ввод клиента приходит на хост через тот же шов**: логика действий игрока не дублируется |
| Движение | `World.move_body()` — чистая функция от тайлов | клиент может двигать своего героя сам, тайлы у него есть |
| Звук | `Sfx.play_at(id, pos)` — позиционный, тише с расстоянием до камеры | события звука по сети — с координатой |
| Тесты | `--test` на 3 сидах, 48 сценариев, `save_test`, CI на Ubuntu | headless-хост и headless-клиенты — те же исполняемые файлы |

### 1.2. Что мешает сетевой игре (найдено чтением кода)

1. **Герой один на весь мир.** `Game.player` — одна ссылка; фантом берёт цель
   `get_first_node_in_group("player")` (`phantom.gd:160`), предмет — тоже (`item_entity.gd:64`),
   директор угрозы (`threat.gd:489`) спавнит у «того самого» героя, туман (`world.gd::_explore_tick`)
   и шлюзы (`world.gd::_defense_tick`) смотрят только на `Game.player`.
2. **Камера у каждого героя.** `Player._ready()` создаёт `Camera2D` и зовёт `make_current()`:
   второй герой в сцене забирает камеру у первого.
3. **Логика перемешана с обратной связью.** В игровом коде 76 прямых вызовов `Sfx.play`,
   `Game.notify`, `UI.flash_*`/`UI.spawn_*`, из них 31 — в `player.gd`. На хосте для чужого героя
   они сыграли бы у хоста: «Рядом нет вентиляции» увидел бы не тот, кто нажал V.
4. **Двойник смотрит в локальный UI.** `Phantom._gazed_at()` проверяет `UI.blocking()` — открыт ли
   инвентарь **у этого процесса**, а не у игрока, на которого смотрит двойник.
5. **Инвентарь правится из панели напрямую.** `inventory_panel.gd` ≈ 20 мест пишет в
   `player.inv.slots` и `chest.slots`, крафт списывает и выдаёт сам. Клиенту нужен слой команд.
6. **Смерть двигает время.** `main.gd::_respawn` переводит часы к рассвету — в коопе один
   погибший отменил бы ночь всем.
7. **Релей берёт детали из одного инвентаря.** `Game.try_finish()` проверяет `player.inv`.
8. **Игра стартует сразу.** Меню нет; `--test`, `--scenario`, `--lore-dump`, `--shot` полагаются на
   немедленный старт `main.tscn`.
9. **Вода — локальная симуляция.** `World._fluid_tick` двигает воду каждые 0.05 с; обрушение
   озера 15×8 меняет до 1252 клеток в секунду (замер § 9.1) — её нельзя считать на двух машинах
   и надеяться на совпадение.

### 1.3. Ограничения (сохраняем из ADR-001)

* Внешних ассетов нет: вид персонажа — код, как и всё остальное.
* Одна зона — один issue — один PR; файлы зон в волне не пересекаются; не больше двух PR в волне.
* PR без замера не принимается; headless-тесты на трёх сидах — часть приёмки.
* Одиночная игра не должна измениться: без сети каждая проверка `--test` и каждый сценарий
  проходят как сейчас.
* Godot запускается в тестах только `--headless`; сетевые тесты слушают только `127.0.0.1`
  (на Windows привязка к внешнему интерфейсу вызывает окно брандмауэра).

## 2. Цели (чем мерим «работает»)

| Метрика | Цель | Как проверяется |
|---|---|---|
| Вход в игру | от «Подключиться» до управления героем ≤ 2 с по LAN | `mp_join_snapshot`, замер мс |
| Задержка своего движения | 0 кадров (движение у владельца) | дизайн § 4.2.3 |
| Задержка действия (копать, E, строить) | ≤ RTT + 1 сетевой такт (≤ 60 мс по LAN) | `mp_actions`, замер на петле |
| Трафик хост → клиент | ≤ 12 КБ/с в обычную ночь, ≤ 32 КБ/с в худшую | `net_probe`/сценарии, § 4.3 |
| Трафик клиент → хост | ≤ 4 КБ/с | то же |
| Кадр хоста | p95 ≤ 16 мс: 4 игрока, 16 фантомов, 130 машин | `mp_perf` (вариант `freeze_probe`) |
| Марионетки | расхождение позиции чужого героя и фантома с хостом ≤ 1 клетки (p95) | `mp_move`, `mp_phantoms` |
| Сохранность предметов | 0 дублей и потерь при одновременных операциях двух игроков | `mp_inventory` (инвариант суммы) |

| Кооп-баланс | давление угрозы на игрока в коопе 0.6–1.0 от одиночного; первая победа 4 игроков 30–45 мин | `mp_balance_*` (MP-K) |
| Одиночная игра | все проверки `--test` и сценарии ADR-001 зелёные без изменений | CI |

## 3. Решения

* **D1. Хост-авторитет на High-level Multiplayer.** `ENetMultiplayerPeer` + `SceneMultiplayer`,
  до 4 игроков, хост — тоже игрок. Мир, машины, фантомы, предметы, инвентари, время и угроза
  считаются **только на хосте**; клиент показывает и предсказывает.
* **D2. Один сетевой узел и свой кодек.** Автозагрузка `Net` с `@rpc`-методами и упакованными
  `PackedByteArray`-пакетами (`NetCodec`). `MultiplayerSynchronizer`/`MultiplayerSpawner` не
  используем (§ 7): замер даёт 188 Б на фантом через `var_to_bytes(Dictionary)` против 12 Б упакованных.
* **D3. Движение — у владельца, действия — у хоста через шов ввода.** Клиент сам двигает своего
  героя (`World.move_body` по своим тайлам) и шлёт хосту позицию и состояние клавиш/мыши.
  Хост кладёт их в `test_input` «прокси»-героя и выполняет действия обычным кодом `Player`
  (копка, постройка, E, V, Q). Хост проверяет правдоподобие позиции. Так делает Террария,
  на которую игра и похожа.
* **D4. Вход в игру = сид + снимок `Save`.** Клиент генерирует мир по сиду из рукопожатия,
  хост шлёт `Save.gather()` (≈ 24 КБ) по надёжному упорядоченному каналу, все последующие
  изменения идут **в том же канале после снимка** — порядок гарантирует ENet.
* **D5. Мир — дельтами батчами.** Изменённые тайлы и уровни воды копятся на хосте и уходят
  раз в сетевой такт (20 Гц) одним пакетом по 4 Б на клетку. Вода считается только на хосте.
* **D6. Частоты.** Физика 60 Гц; состояние (игроки, фантомы, летящие предметы) 20 Гц ненадёжно;
  ввод клиента 30 Гц ненадёжно со счётчиками нажатий; машины в зоне интереса 4 Гц и только
  изменённые; глобальное (время, угроза, этап) 1 Гц и по событию. Чужие герои и фантомы
  рисуются на 100 мс в прошлом с интерполяцией.
* **D7. Поиск игр — запрос/ответ по UDP.** Клиент шлёт широковещательный запрос на порт 24643,
  хост отвечает **юникастом**. Клиенту (в том числе Android) не нужно принимать broadcast.
  Ручной ввод IP — всегда рядом.
* **D8. Меню, профиль и параметры вида.** Экран меню перед игрой; профиль в `user://profile.cfg`:
  ник, uid и **параметры** вида — цвет скафандра, шлем/визор, аксессуар, рюкзак/баллоны (индексы,
  в сети — `u16`). Как скафандр выглядит, решает ADR-003 (#84, визуальный стиль, силуэт
  «Кербер-9»): нынешний герой слишком похож на крюмейта Among Us. ADR-002 фиксирует только
  параметры, их передачу и один шов рисования `Avatar` для игры, превью в лобби и двойника.
  Любые аргументы командной строки — старый немедленный старт (CI не меняется).
* **D9. Угроза растёт с числом игроков, но не линейно.** Бюджет ночи × (1 + 0.5·(N−1)),
  cap + 2·(N−1) (не выше 16 — предел `freeze_probe`), интервал ÷ (1 + 0.35·(N−1)); спавн —
  у наименее «занятого» игрока. Формулы и константы — в `Balance` (§ 4.7).
* **D10. Общее — команде, личное — игроку.** Данные, исследования, журнал, сундуки, туман
  (общая карта), этап цели — общие. Инвентарь, HP, укрытие, кулдауны — личные. Терминал даёт
  данные один раз на команду.
* **D11. Смерть в коопе не трогает часы.** Погибший 15 с смотрит глазами товарища и возрождается
  на базе; мешок с хотбаром 120 с может поднять только владелец. Вся команда погибла — правило
  одиночной игры (рассвет).
* **D12. Двойник среди своих.** В сети двойник берёт **вид и ник товарища** и охотится на
  самого отбившегося. Распознать: перекличка (G), маячки на миникарте, замирание под взглядом,
  тишина, удар (свой не получает урон, двойник — «глючит»).
* **D13. Сохраняет только хост, паузы нет.** Файл версии 2 хранит игроков по uid профиля;
  вернувшийся игрок получает свои вещи. Автосохранение хоста на каждом рассвете.
* **D14. Тесты — несколько процессов.** Хост-процесс сценария запускает клиентов
  `OS.create_process` на `127.0.0.1` (замер: 467 мс на запуск, вход и снимок). В одном процессе
  проверяется только транспорт и кодек (несколько `SceneMultiplayer` на поддеревьях).
* **D15. Фундамент первым** (как ADR-001 D12): MP-A резервирует автозагрузку `Net`, кодек,
  константы `Balance`, крюки в `Game`/`main.gd` и сетевой тест-харнесс; после него системные PR
  работают в своих новых файлах `scripts/net/*` и в секциях «СЕТЬ (ADR-002)» чужих файлов.

## 4. Дизайн

### 4.1. Сеть: топология, роли, каналы

```
            ┌───────────── ХОСТ (игрок 1) ─────────────┐
            │ мир, вода, машины, фантомы, угроза, время │
 клиент 2 ◄─┤ инвентари всех, проверка позиций          ├─► клиент 3, 4
  ввод+поз. │ Player LOCAL + Player PROXY ×(N−1)        │   ввод+поз.
            └───────────────────────────────────────────┘
```

* **Транспорт.** `ENetMultiplayerPeer.create_server(24642, 3)` (хост + 3 клиента), клиент —
  `create_client(ip, 24642)`. Тесты: `set_bind_ip("127.0.0.1")`. Таймаут пира
  `set_timeout(32, 3000, 8000)` — обрыв замечается за 3–8 с.
* **Рукопожатие** — `SceneMultiplayer.auth_callback`, таймаут 3 с. Клиент шлёт
  `{proto, build, uid, nick, look}`; хост проверяет: `proto == Net.PROTO`, `build` равен своему
  (`application/config/version` из #80, иначе `"dev"`), есть свободный слот, ник валиден;
  повтор ника → «Аня 2». Ответ: `{ok, reason, seed, slot, session_name}`. Отказы с причиной:
  «мест нет», «версии разные: хост 0.5.0, у вас 0.4.2», «игра закрыта».
* **Версии телефона и ПК.** Релизы собираются по кнопке (`workflow_dispatch`, #80), APK подписан
  постоянным ключом — значит, игроки ставят сборки разных релизов. Правило подключения:
  `Net.PROTO` равен **всегда**; `build` (`application/config/version`, его пишет релиз) равен
  точно, кроме случая, когда оба `"dev"` (локальные сборки разработчиков). Номер версии виден в
  меню и в списке найденных игр («другая версия» — серым, подключиться нельзя). `PROTO` поднимается
  при любой смене кодека, порядка `IDs` или таблиц `DB`: `net_test` хранит хэш схемы сообщений
  и числа тайлов/предметов/рецептов и падает, если схема изменилась, а `PROTO` — нет.
  Заметки релиза (#80) пишут «сетевая совместимость: протокол N».
* **Роли процесса**: `OFFLINE` (одиночная — всё как сейчас), `HOST`, `CLIENT`.
  `Net.is_authority()` — истина в `OFFLINE` и `HOST`; этой одной проверкой системы решают,
  считать им или показывать.
* **Каналы ENet** (`transfer_channel` у `@rpc`):

| Канал | Режим | Что идёт |
|---|---|---|
| 0 | надёжный упорядоченный | снимок, батчи тайлов и воды, постройка/снос машин, появление/исчезновение фантомов и предметов, глобальное состояние, события (звук, FX, уведомления для всех) |
| 1 | ненадёжный упорядоченный | пакет состояния 20 Гц: игроки, фантомы, летящие предметы |
| 2 | надёжный | личное: инвентарь владельца, открытый сундук, уведомления игроку, ответы на команды |
| 3 | ненадёжный упорядоченный | клиент → хост: ввод и позиция 30 Гц |

Ненадёжный упорядоченный канал сам выбрасывает устаревшее: на петле при двух тактах за кадр
доставлено 241 из 300 пакетов — это нужное поведение для состояния (новое затирает старое).

* **Такты.** Физика 60 Гц (как сейчас). Сетевой такт хоста — каждый 3-й физический кадр (20 Гц).
  Ввод клиента — каждый 2-й (30 Гц). Машины — 4 Гц по кругу. Глобальное — 1 Гц.

### 4.2. Что и как синхронизируется

#### 4.2.1. Сводная таблица

| Что | Кто считает | Как попадает к клиенту | Частота | Байт |
|---|---|---|---|---|
| Мир при входе | хост | сид (рукопожатие) + `Save.gather()` без раздела `player`, ZSTD | раз | ≈ 24 КБ |
| Тайлы | хост (`World.set_tile`) | батч `u32 = idx(17 бит) · id(8 бит)` | 20 Гц, если не пусто | 4 / клетка |
| Вода | хост (`_fluid_tick`) | батч `u32 = idx · уровень(4 бита)` по «грязным» клеткам такта | 20 Гц | 4 / клетка |
| Туман | каждый процесс сам | открывается вокруг **всех** героев по их позициям | — | 0 |
| Постройка / снос машины | хост | событие: `save_state()` машины (`var_to_bytes`, 184–780 Б) / клетка | по событию | |
| Состояние машин | хост | `net_state()` машины в зоне интереса, только изменённые | 4 Гц | 6 (станок) – 4+3·предметов (лента) |
| Предметы на земле | хост (физика, подбор) | появление `{id, count, pos, vel, bag}`, приземление, исчезновение; в полёте — в пакете состояния | событие + 20 Гц | 8 в полёте |
| Фантомы | хост (ИИ, путь, урон) | появление `{id, kind, pack, имя, вид}`, позиция и флаги в пакете состояния, гибель — событие | 20 Гц | 12 |
| Свой герой | **владелец** (движение) / хост (HP, флаги) | клиент → хост: позиция; хост → владельцу: HP, укрытие, оглушение, смерть, кулдауны | 30 / 20 Гц | 26 / 10 |
| Чужие герои | хост | пакет состояния: позиция, скорость, флаги, клетка копки, предмет в руке | 20 Гц | 18 |
| Время, смена, угроза, этап, данные, релей | хост | глобальный пакет; время клиент двигает сам и подтягивает | 1 Гц + событие | 40 |
| Исследования, главы, обрывки | хост (`Tech`) | событие | по событию | |
| Инвентари | хост | владельцу — полный (36 слотов × 3 Б) при изменении | по событию | 112 |
| Открытый сундук | хост | тем, у кого он открыт | по событию | 76 |
| Звук, FX, уведомления | хост | событие с координатой; звук играет `Sfx.play_at` у тех, кто слышит | по событию | 12–24 |

**Зона интереса** клиента: прямоугольник ±720×420 px вокруг его героя (обзор 1280×720 при
`zoom 2.2` — 582×327 px, с `stretch/aspect=expand` на телефоне 20:9 — до 730×327 px). Фантомы,
машины и предметы вне зоны не шлются; тайлы и вода — всегда (они нужны миникарте и туману).

#### 4.2.2. Вход в игру (join in progress)

1. Рукопожатие → клиент получает сид, слот, имя сессии. Экран «Загрузка мира…».
2. Клиент: `World.generate(seed)` (0.96 с на сид 31337: gen 776 + astar 39 + sync 85 + свет 62 мс),
   `Game.reset_run()`, затем RPC `ready_for_snapshot`.
3. Хост: `Save.gather_join()` — тот же словарь, что `Save.gather()`, без раздела `player`
   (2.5 мс + encode 3.4 мс на базе в 130 машин) → канал 0. С этого момента клиент в рассылке
   дельт; они встают в канал **после** снимка.
4. Клиент: `Save.apply_join(d)` — `apply()` без героя и без пересчёта питания (машины — марионетки);
   ставит героев всех игроков; переходит в игру. Ожидаемо ≈ 1.1–1.3 с от подключения.
5. Сверка: раз в 30 с хост шлёт `hash(World.tiles)`; расхождение → клиент просит снимок
   заново (тот же путь, 24 КБ). В тестах сверка идёт на каждом барьере.

#### 4.2.3. Игроки: движение у владельца, действия через шов ввода

У `Player` появляется роль `net_role`:

| Роль | Где | Движение | Действия (`_handle_input`) | HP, инвентарь, флаги | Камера, обратная связь |
|---|---|---|---|---|---|
| `LOCAL` | одиночная; свой герой хоста | как сейчас | как сейчас | как сейчас | да |
| `PROXY` | хост, чужой герой | **не интегрирует**: позиция из сети после проверки | **да**: `test_input` ← пакет ввода | да, авторитетно | нет; уведомления/вспышки/тряска — владельцу событием |
| `OWNER` | клиент, свой герой | **да**, `World.move_body` | нет: ввод уходит хосту | из сети | да |
| `PUPPET` | клиент, чужой герой | интерполяция | нет | из сети (для рисования) | нет |

**Пакет ввода** клиент → хост (канал 3, 30 Гц, 26 Б): `seq u16`; клавиши `u32` (A, D, ←, →, W, ↑,
пробел, Shift, E, Q, V, G, ЛКМ, ПКМ, «окно открыто»); мышь в мире `2×u16` px (мир 10240×2880);
выбранный слот `u8`; счётчики нажатий E/Q/V/G по 4 бита (`u16`) — фронт не теряется при потере
пакета; позиция `2×f32`, скорость `2×s16`, флаги `u8` (facing, on_ground).
Пакет собирается **из шва** (`_key`, `_mouse_down`, `_mouse_pos`) — сенсорное управление #81,
которое кладёт виртуальные клавиши в тот же шов, работает по сети без доработок.

**Проверка позиции на хосте**: `|Δpos| ≤ (SPRINT_SPEED + MAX_FALL)·dt·1.5 + 8 px` и тело не в
сплошной клетке. Иначе хост шлёт владельцу поправку (жёсткую). Поправки с хоста владельцу:
отбрасывание от удара (`knock`), укрытие (`hiding`, скорость 0.4), оглушение (`_stun`),
смерть и респаун (телепорт). Владелец им подчиняется сразу; до прихода поправки — максимум RTT.

**Копка и постройка** идут на хосте по удержанию ЛКМ/ПКМ из пакета ввода: прогресс копки,
`mining_cell`, предмет в руке приходят владельцу и марионеткам и рисуются как сейчас.
Задержка = RTT + ≤ 50 мс (такт) — на LAN незаметно, копка длится 0.15–4 с.

**Обратная связь** `Player` идёт через три обёртки (секция «СЕТЬ» в `player.gd`): `_notify()`,
`_sfx_here()` (звук `play_at` в точке героя всем, кто слышит), `_feedback(kind)` (вспышка урона,
тряска камеры). У `PROXY` они уходят владельцу; у `LOCAL` работают как сейчас. 31 вызов
в `player.gd` переводится на обёртки — список проверяет сценарий `mp_feedback`.

**Камера** создаётся только у `LOCAL`/`OWNER`. **Ники** над головами рисует `Avatar`
(шрифт `ThemeDB.fallback_font` 8 px, как имя двойника), цвет — светлый тон скафандра.

#### 4.2.4. Машины

* На клиенте `MachineBase._process` не работает (`Net.is_authority()` в начале): ни прогресса,
  ни выдачи, ни питания. Остаются анимация и перерисовка по полученному состоянию.
* `net_state()`/`apply_net_state()` — компактная пара на машину, рядом с `save_state()`:
  станки — прогресс `u8`, питание/efficiency `u8`, hp `u8`, флаги; лента — `dir` + предметы
  по 3 Б (`id`, `count`, `pos·255`); турель — угол ствола `u8`; ТЭЦ — топливо `u8`, вкл/выкл.
* Хост раз в 0.25 с обходит машины в зонах интереса и шлёт только те, чей `net_state()` изменился.
  Ленты клиент между пакетами экстраполирует (`pos += SPEED·dt`, не дальше конца ленты, без
  передачи соседу) — предметы едут плавно.
* Выстрел турели (`World.turret_fired`), сломанная решётка, браун-аут — события канала 0.

#### 4.2.5. Фантомы

* ИИ, путь, свет, урон — только на хосте. На клиенте `Phantom` — марионетка: `_physics_process`
  только интерполирует, `_draw` прежний (данные для него — в пакете).
* Пакет фантома 12 Б: `id u16`, позиция `2×u16` px, скорость `2×s8` (/16), `u8` = тип(3) · состояние(2)
  · facing(1) · frozen(1) · оглушён(1), hp `u8` (доля), оглушение `u8` (×20), флаги `u8`.
* Цель — **ближайший живой, не спрятавшийся, на связи** герой (пересчёт раз в 0.5 с, как
  `SEEK_INTERVAL`); шум и обзор — по этому герою. Двойник замирает, если на него смотрит
  **любой** герой; «окно открыто» берётся из пакета ввода, а не из `UI.blocking()` хоста.
* Чёрный ящик, подобранный любым игроком, вскрывается на хосте (`Threat` подписан на все
  инвентари): данные и обрывок — команде.

#### 4.2.6. Время, угроза, цель

Клиент двигает `time_of_day` сам (`Game._process` — та же формула) и подтягивается к хосту,
если разница > 0.002 цикла (0.5 с). Смена, этап, данные, таймер релея, бюджет и активность ночи —
из глобального пакета; рассвет, «Смена N», этап цели — события с уведомлением всем. Питание,
цель, релей и директор угрозы на клиенте не считаются.

#### 4.2.7. Инвентари, крафт, сундуки (слой команд `InvOps`)

Панель инвентаря больше не пишет в слоты напрямую, а зовёт атомарные команды:
`move(откуда, слот, куда, слот, n)`, `split`, `take_all`/`put_all` (сундук), `craft(рецепт, раз)`,
`drop(слот, n)`, `select(i)`, `unlock(узел)`. В одиночной и у хоста команда выполняется сразу
тем же кодом, что сейчас в панели; у клиента — RPC хосту (канал 2), хост проверяет (дистанция
до сундука, наличие, место) и рассылает итог. «Предмет в руке» — состояние окна клиента,
в мир не попадает до команды. Два игрока у одного сундука: хост выполняет команды по очереди,
опоздавшая получает отказ и свежее содержимое. Инвариант «сумма предметов» проверяет `mp_inventory`.

### 4.3. Трафик

Накладные расходы измерены на петле (§ 9.1): ENet + RPC ≈ 44 Б на пакет, плюс UDP/IP 28 Б.
Считаем 72 Б на датаграмму.

**Хост → один клиент, худшая ночь** (4 игрока, 16 фантомов в зоне интереса, база из 130 машин
в зоне, обрушение озера):

| Предметы в полёте: ≤ 16 × 8 | 1 | 20 | 128 | 2 560 |
| Заголовок пакета состояния | 1 | 20 | 8 | 160 |
| Тайлы (≈ 20 изменений/с) | 0 | 20 | — | 80 |
| Вода, пик обрушения (1252 кл./с, 2.4 с) | 0 | 20 | — | 5 008 |
| Машины: 60 лент × 10 + 70 × 6 | 0 | 4 | 1 020 | 4 080 |
| События (≈ 40/с × 16) | 0 | — | — | 640 |

| Заголовки: ≈ 45 датаграмм/с × 72 | | | | 3 240 |
| **Итого** | | | | **≈ 21.1 КБ/с (169 кбит/с)** |

* **Обычная ночь** (8 фантомов в зоне, 30 машин, без воды, 4 летящих предмета): ≈ 8.6 КБ/с.

### 4.4. Лаг и обрыв

| Ситуация | Что видит клиент | Что делает хост |
|---|---|---|
| Пакетов состояния нет > 0.5 с | значок «Связь с хостом прерывается…»; свой герой ходит; марионетки экстраполируются ≤ 150 мс и стоят | — |
| Ввода от клиента нет > 1 с | — | прокси «без связи»: ввод сброшен, фантомы его не выбирают целью, урон не получает |
| Таймаут ENet (3–8 с) | «Связь с хостом потеряна» → меню | прокси убран, состояние «запарковано» по uid в `Net.parked`, всем — «Аня потеряла связь» |
| Тот же uid вернулся | позиция, HP, инвентарь как были | состояние из `Net.parked` (или из сохранения) |
| Хост вышел или упал | «Хост завершил игру» → меню | — (передачи хоста нет, § 7); потерю ограничивает автосохранение на рассвете |
| Потери Wi-Fi до 5 % | рывков нет: состояние ненадёжное, интерполяция 100 мс | надёжный канал 0 повторяет сам; задерживаются только дельты мира |
| Медленный кадр хоста | интерполяция поглощает до 100 мс | — |

Отключение не наказывается: хотбар не падает, герой не умирает.

### 4.5. Поиск игр в локальной сети

* **Порт** 24643/UDP (игра — 24642). Хост слушает `bind(24643, "*")` (тесты — `127.0.0.1`).
* **Запрос**: экран «Найти игру» шлёт `"GCQ1" + proto u16` на `255.255.255.255:24643` и на
  направленный broadcast каждого локального IPv4 из `IP.get_local_interfaces()` (маску Godot не
  отдаёт — считаем /24, домашний случай) сразу, через 0.5 с и дальше каждые 1.5 с.
* **Ответ** хоста — **юникастом** на адрес запроса: `"GCA1" + JSON {v, proto, build, name, host,
  n, max, port, day}` — 107 Б в замере, круг 0.5 мс на петле.
* **Список**: ключ `ip:port`; имя игры, ник хоста, игроков n/max, пинг (время ответа), смена;
  другая версия — серым «другая версия»; запись живёт 4 с без ответа. Кнопка «Обновить».
* **Подключиться по IP**: поле `IPv4[:порт]` или имя хоста (`IP.resolve_hostname`), последние 5
  адресов — в профиле. Экран хоста показывает свои адреса из частных диапазонов
  (10/8, 172.16/12, 192.168/16) крупно — для друга с телефона.
* **Android.** Клиенту принимать broadcast не нужно (ответ юникастом), значит
  `WifiManager.MulticastLock` ему не требуется. **Хост на Android** должен принять запрос-broadcast;
  на части устройств без MulticastLock он до приложения не доходит, а в ядре Godot API для блокировки
  нет. Решение: разрешения `INTERNET`, `ACCESS_NETWORK_STATE`, `ACCESS_WIFI_STATE`,
  `CHANGE_WIFI_MULTICAST_STATE` закладывает #80; если ручной тест покажет, что телефон-хост не
  виден, — маленький плагин MulticastLock отдельным issue (§ 8, вопрос 9). До того — IP на экране
  хоста и «Подключиться по IP». Точка доступа на телефоне (хост раздаёт Wi-Fi) работает так же.
* **Брандмауэр Windows** спрашивает разрешение при первом «Создать игру» — строка в README.

### 4.6. Меню, профиль, вид персонажа

**Главный экран** (`scenes/menu.tscn`, `scripts/ui/main_menu.gd`): название, живое превью героя
(дышит, раз в 2 с поворачивается), поле ника, кнопки «Одиночная игра», «Создать игру»,
«Найти игру», «Подключиться по IP», «Вид персонажа», «Выход».

* **Совместимость.** `run/main_scene` остаётся `main.tscn`. `main.gd` в начале `_ready()`: если
  пользовательских аргументов нет и сессия не задана (`Net.session.is_empty()`), а сцена меню
  существует — `change_scene_to_file(menu)`. Любой аргумент (`--test`, `--scenario=`, `--seed=`,
  `--lore-dump`, `--shot`, `--hardcore`, `--mp-*`) — старый немедленный старт. CI не меняется.
* **Ник**: после `strip_edges()` 2–16 символов; буквы `A–Z a–z А–Я а–я Ё ё`, цифры, пробел, `_ - .`;
  первый и последний — буква или цифра; двух пробелов подряд нет. Ошибка — подписью под полем,
  кнопки игры неактивны. Повтор ника в сессии хост разводит: «Аня 2».
* **Вид — только параметры.** Облик скафандра экспедиции «Кербер-9» (силуэт, пропорции, шлем,
  отдельные руки и ноги, палитра) проектирует ADR-003 (#84) вместе со стилем всего мира. Здесь —
  что игрок выбирает и как это едет по сети (`Look`, `u16`, 4 бита на часть):

| Параметр | Индекс | Сколько вариантов | До ADR-003 |
|---|---|---|---|
| Цвет скафандра | 0..15 | палитра ADR-003, ≤ 16 | 8 цветов-заглушек, нынешний красный — индекс 0 |
| Шлем / визор | 0..15 | по ADR-003, ≤ 16 | только 0 (нынешний визор) |
| Аксессуар (антенна, фонарь, …) | 0..15 | по ADR-003, ≤ 16 | только 0 (огонёк на шлеме) |
| Рюкзак / баллоны | 0..15 | по ADR-003, ≤ 16 | только 0 (нынешний рюкзак) |

  Неизвестный индекс (сборка новее, чем у собеседника, при равном `PROTO` не бывает, но файл
  профиля может быть чужим) рисуется как 0. Кнопка «Случайно» выбирает только из вариантов,
  которые есть в `Avatar.VARIANTS`.
* **Шов рисования** — `Avatar.draw(canvas, layout, look, state)` (`scripts/core/avatar.gd`):
  его зовут `Player._draw`, превью в меню и лобби и двойник. MP-B выносит в него нынешний
  рисунок героя без изменений (цвет — из палитры по `look`); новый скафандр по ADR-003 —
  отдельный PR MP-L, который меняет только `Avatar` и `Player.body_layout()` (шов #58: части
  задаются «лицом вправо» и зеркалятся `_mirror` по `facing`; новые ключи — руки, шлем, баллоны —
  тем же способом) и обновляет проверки `anim_test`.
* **Профиль**: `user://profile.cfg` (`ConfigFile`): `[profile] uid` (случайные 64 бита, создаются
  один раз — по нему хост узнаёт вернувшегося), `nick`, `look`; `[net] recent_ips`, `port`.
* **«Создать игру»**: имя игры («Экспедиция <ник>», 1–24 символа), сид (пусто — случайный; текст —
  `hash()`), мест 2–4 (по умолчанию 4), порт (24642), «Продолжить сохранение» (список сетевых
  сохранений). Хост сразу входит в игру; остальные входят в любой момент — отдельной комнаты
  ожидания нет (§ 7).
* **«Найти игру» / «Подключиться по IP»** — § 4.5; экран состояния «Подключение… / Загрузка мира… /
  Ошибка: <причина>».
* **В игре**: Esc — «Продолжить / Отключиться» (клиент), «Завершить игру (с сохранением)» (хост),
  «Выйти в меню» (одиночная). В сети Esc паузу не ставит.
* **Командная строка** (для разработки и тестов, MP-A): `--mp-host[=порт]`, `--mp-join=ip[:порт]`,
  `--nick=`, `--look=`, `--mp-bind=127.0.0.1`, `--mp-scenario=<имя|all>`, `--mp-clients=N`.

### 4.7. Геймплей и баланс кооператива

N — число игроков на связи в момент начала ночи (для cap — текущее).

**Угроза** (`Threat`, поверх формул ADR-001 § 4.5; при N = 1 всё как сейчас):

```
T      = как сейчас (смена + генераторы + лампы + релей) — база общая
B_N    = (3 + 2·T) · (1 + MP_BUDGET_PER_PLAYER·(N − 1))            # 0.5
cap_N  = min(min(2 + смена, 10) + MP_CAP_PER_PLAYER·(N − 1), MAX_PHANTOMS)   # +2, ≤ 16
cap_N(релей) = min(RELAY_HOLD_CAP + MP_CAP_PER_PLAYER·(N − 1), MAX_PHANTOMS)
interval_N = clamp((7 − 0.5·T) / (1 + MP_INTERVAL_PER_PLAYER·(N − 1)), MP_SPAWN_INTERVAL_MIN, 7)  # 0.35, 1.5 с
спавн  — у героя с наименьшим числом фантомов-преследователей (ничья — дальний от базы),
         из трёх ближайших к нему вентиляций, как сейчас
двойник — не больше одного (§ 8, вопрос 2)
```

| N | Бюджет × | Ночь 1: B / cap / интервал | Ночь 4: B / cap | Релей: cap | Бюджет на игрока от одиночного |
|---|---|---|---|---|---|
| 1 | 1.0 | 6 / 3 / 6.3 с | 13 / 6 | 10 | 1.00 |
| 2 | 1.5 | 9 / 5 / 4.6 с | 19.5 / 8 | 12 | 0.75 |
| 3 | 2.0 | 12 / 7 / 3.7 с | 26 / 10 | 14 | 0.67 |
| 4 | 2.5 | 15 / 9 / 3.0 с | 32.5 / 12 | 16 | 0.63 |

Почему так: четверо бьют вчетверо сильнее, но они разбросаны по шахтам; на базу (тень, рой,
копатель) давление растёт полностью — команда защищает одну базу. «Бюджет на игрока» 0.63–0.75
компенсирует то, что фантом идёт к ближайшему, а игроки сбиваются в группы. Cap упирается в
`MAX_PHANTOMS = 16` — предел, принятый по `freeze_probe` в #27; поднимать его — только с замером.
Точные множители подбирает MP-K ботовыми прогонами.

| Миникарта | свой маркер всегда; товарищ — если ближе `MP_TEAM_RADIO_TILES = 20` клеток или в радиусе питания любого работающего генератора («маячок скафандра питается от сети базы»); двойник — никогда |
| Укрытие | **один герой на вентиляцию**: «Вентиляция занята: Аня»; товарищи видят ник у занятой вентиляции |
| Огонь по своим | нет: удар по товарищу — «клац» и `MP_FRIENDLY_SLASH_CD = 1 с`; импульс Q героев не трогает |
| Статистика | общая на команду + личная по uid для экрана итогов |

**Смерть и респаун в сети**

* Погибший: мешок с хотбаром на месте смерти (как сейчас), поднять его 120 с
  (`MP_BAG_OWNER_LOCK`) может только владелец, потом — любой (отнести в сундук).
* Экран «ТЕБЯ НАШЛИ» с эпитафией и таймером `MP_RESPAWN_DELAY = 15 с`; камера следует за живым
  товарищем (A/D — следующий). Респаун в капсуле на базе, **время не двигается**.
* Погибли все живые сразу (вайп) — правило одиночной: через `RESPAWN_DELAY` все на базе, часы
  к рассвету.
* `--hardcore` в сети: погибший — зритель до конца забега; погибли все — конец (экран для всех).

**Релей вчетвером**

* **Вклад деталей** (во всех режимах): E у ядра сдаёт из своего инвентаря то, чего ядру ещё не
  хватает (`Game.relay_deposit`), HUD показывает «Релей: 18/24 жел. пластин…». Набрано всё —
  удержание E 3 с запускает отсчёт. В одиночной с полным набором — как сейчас за одно нажатие.
* **Зона удержания** (только в сети, § 8 вопрос 1): отсчёт 180 с идёт, пока хотя бы один живой
  не спрятавшийся герой ближе `MP_RELAY_HOLD_RADIUS_TILES = 12` клеток к ядру; иначе стоит
  (не сбрасывается) и HUD предупреждает «Сигнал без присмотра». Один держит ядро, остальные —
  генераторы и турели: роли появляются сами.

**Паузы нет** в сети. Время суток общее, «сон до утра» не вводим.

### 4.8. Двойник среди своих («Among Us»)

| Правило | Одиночная (как сейчас) | Сеть |
|---|---|---|
| Когда | с ночи 6 и на релее, не больше одного | так же |
| Жертва | герой | самый отбившийся: максимум дистанции до ближайшего товарища |
| Имя над головой | `Lore.impostor` | **ник товарища**, который дальше всех от жертвы и жив |
| Вид | спрайт героя | **вид того же товарища** (`Avatar`, его `Look`) |
| Если в сети один живой | — | как в одиночной |

**Как распознать** (от сильного признака к слабому):

1. **Два одинаковых ника сразу на экране** — один из них ненастоящий.
2. **Перекличка (G)**: любой жмёт G (кулдаун `MP_ROLLCALL_COOLDOWN = 20 с`) — у всех на HUD
   «Аня: перекличка!»; настоящие отвечают своим G, огонёк на шлеме горит зелёным
   `MP_ROLLCALL_LIGHT = 4 с`. Огонёк двойника остаётся красным.
3. **Миникарта**: двойника на ней нет, а маячок настоящей Ани (в зоне питания или в 20 клетках)
   может быть совсем в другом месте.
4. **Замирает под взглядом** любого героя (правило ADR-001); настоящий игрок под взглядом не
   замирает — но может просто стоять у монитора.
5. **Тишина**: ни шагов, ни звука копки; он никогда не копает и не строит.
6. **Визор мерцает красным**, под взглядом — чаще (уже есть).
7. **Удар**: свой урона не получает (клац + кулдаун — проверка стоит времени), двойник получает
   урон и на `MP_DOPPEL_REVEAL = 1.5 с` «глючит» — проступает его настоящий облик. Подойти на
   удар — значит подойти на его удар (40 урона).

Награда за убийство — как сейчас: чёрный ящик с финальной главой.

### 4.9. Сохранение сетевой игры

* Сохраняет **только хост**: F5 и автосохранение на каждом рассвете в слот
  `mp_<имя игры>_auto`. У клиента F5/F9 молчат с подсказкой «Сохраняет хост». F9 в сети выключена:
  загрузка — из меню при создании игры.
* **Формат версии 2** (`Save.VERSION = 2`): к словарю добавляются `session {name, max}` и
  `players {uid: {nick, look, state = Player.save_state(), stats}}` — и подключённые, и
  запаркованные. Раздел `player` остаётся (герой хоста), поэтому файл версии 1 грузится как
  одиночный, а одиночная игра читает версию 2, беря только `player`.
* Загрузка сетевого сохранения: герой хоста — из своего uid; остальные ждут в `Net.parked`
  и получают своё при входе. Незнакомый uid — стартовый набор у капсулы.
* Фантомы, как и в #37, поштучно не пишутся — возвращаются в очередь ночи.

### 4.10. Тестирование

**Почему не «всё в одном процессе».** `World`, `Game`, `Threat`, `Tech`, `UI` — автозагрузки:
одна копия на процесс. Два мира (хоста и клиента) в одном процессе потребовали бы переписать
синглтоны в экземпляры сессии — это переделка всей игры (§ 7). Поэтому два уровня:

| Уровень | Что | Как | Время |
|---|---|---|---|
| 1. Один процесс | кодек (упаковка и распаковка каждого сообщения, граничные значения), рукопожатие (таблица отказов), транспорт: хост + 3 клиента — свои `SceneMultiplayer` на поддеревьях `/root/H`, `/root/C0..2` через `SceneTree.set_multiplayer(api, путь)`; поиск запрос/ответ на `127.0.0.1` | `tools/net_test.gd` (`--script`) | < 10 с (замер: подключение 46 мс, снимок 2 мс) |
| 2. Несколько процессов | настоящая игра: хост и клиенты headless | `godot --headless --path . -- --mp-scenario=<имя> --seed=31337` | 1–3 с на процесс (замер: клиент-процесс 467 мс до выхода) |

**Харнесс уровня 2** (MP-A, `tools/mp/`):

* Хост-процесс читает `--mp-scenario`, поднимает сервер на `127.0.0.1:(24700 + pid % 200)`, запускает
  `--mp-clients` клиентов: `OS.execute_with_pipe(OS.get_executable_path(), ["--headless", "--path",
  ".", "--", "--mp-join=127.0.0.1:<порт>", "--mp-role=<i>", "--mp-scenario=<имя>", "--seed=<сид>"])`.
* Сценарий — наследник `MpScenarioBase` (как `ScenarioBase`, тот же шов ввода): `run_host()` и
  `run_client(i)`. Точки синхронизации — `await barrier("имя")` (RPC: все дошли). Проверки печатаются
  как сейчас (`OK`/`FAIL`), вывод клиентов хост перепечатывает с префиксом `[c1]`.
* Итог — общий `ИТОГ: проверок N, провалов M`; код возврата — максимум из процессов; зависший
  клиент убивается по таймауту сценария (90 с), это провал.

**Сценарии `mp_*`** (каждый PR добавляет свои, `tools/mp/scenarios/`):

## 7. Отклонённые альтернативы

* **Детерминированный lockstep (как Factorio).** Нужна побитовая детерминированность всей
  симуляции: GDScript на `float`, `delta` кадра в физике, `randf()` в ИИ и FX, порядок обхода
  словарей — любое расхождение рушит игру без восстановления. Пришлось бы переписать симуляцию
  на фиксированную точку.
* **Полный хост-авторитет движения с предсказанием и откатом.** `Player._physics_process`
  смешивает движение, таймеры и действия; отделять «чистый шаг» и переигрывать ввод ради
  античита, ненужного в кооперативе по LAN, — дорого. Принятый вариант (D3) даёт 0 кадров
  задержки и правдоподобную проверку на хосте.
* **Без предсказания** (хост двигает всех, клиент только смотрит). На Wi-Fi с джиттером 10–30 мс
  и пакетами 20 Гц герой «плывёт» за клавишей на 3–5 кадров.
* **`MultiplayerSynchronizer` и `MultiplayerSpawner` на каждый узел.** Пакет на узел, свойства
  через `var`-сериализацию (×15 к размеру по замеру), тайлы и воду так не выразить, сущности
  создаются кодом, а не сценами. Один узел `Net` с кодеком проще тестировать в headless.
* **Голый `ENetConnection` без `SceneMultiplayer`.** Теряем готовые аутентификацию, маршрутизацию
  RPC и id пиров; выигрыш — десятки байт на пакет, которые на LAN не важны.
* **WebSocket/WebRTC.** Для LAN лишние: TCP-WebSocket блокирует очередь при потере пакета,
  WebRTC требует сигнального сервера. ENet — UDP с надёжными и ненадёжными каналами.
* **Передача хоста.** Клиент не держит ИИ, воду, инвентари других — передавать нечего. Потерю
  ограничивает автосохранение на рассвете.
* **Клиенты слушают broadcast-анонсы хоста.** Два клиента на одной машине (тесты) не могут
  занять один порт; Android требует MulticastLock на приём. Запрос/ответ юникастом снимает оба.
* **Multicast-поиск.** На Android нужен MulticastLock, дешёвые роутеры режут IGMP.
* **Две игры в одном процессе для тестов.** Автозагрузки — синглтоны процесса; переделка
  `World`/`Game`/`Threat`/`Tech`/`UI` в экземпляры сессии — переписывание игры. В одном процессе
  проверяем только транспорт и кодек.
* **Личный туман у каждого.** Больше данных в сохранении и снимке, меньше кооператива («где ты
  был — я не вижу»). Общая карта считается локально и не стоит трафика.
* **Общий инвентарь команды.** Ломает «кто что несёт», хаос при одновременном крафте, убивает
  смысл мешка после смерти. Общие — сундуки.
* **Комната ожидания с готовностью.** Вход посреди игры нужен всё равно (обрыв, опоздавший);
  второй путь входа — лишнее состояние.
* **Пауза или голосование за паузу в сети.** Один игрок останавливает троих; ночь теряет напряжение.
* **Сдвиг времени к рассвету при смерти одного.** Отменяет ночь всей команде (§ 1.2, п. 6).

## 8. Открытые вопросы к владельцу

1. **Зона удержания релея в одиночной игре.** В сети отсчёт стоит, если у ядра никого нет.
   Применить и в одиночной? Предложение: только в сети — одиночный баланс уже откалиброван PR-J.
2. **Двойников при 4 игроках: один или два?** Предложение: один — иначе перекличка и маячки
   шумят; вернуться после MP-K.
3. **Масштабировать ли `relay_req` и цены технологий от N?** Предложение: нет; если MP-K
   покажет первую победу вчетвером быстрее 30 мин — `relay_req × (1 + 0.25·(N−1))`.
4. **Огонь по своим.** Предложение: выключен (клац и кулдаун удара). Включить частично (50 %)?
5. **`--hardcore` в сети**: погибший — зритель до конца забега или до рассвета?
   Предложение: до конца.
6. **Маячки товарищей на миникарте** — только в зоне питания и в 20 клетках (как в ADR) или
